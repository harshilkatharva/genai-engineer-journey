Testing meant enumerating cases. Debugging meant tracing execution line by line. The entire discipline of software correctness was built on the assumption that a given input always produces a given output.\nLarge Language Models break that assumption, and with it, they break a lot of assumptions baked into how we build, test, and ship software.\nAn LLM-powered application doesn't execute a fixed program - it generates a plausible one at inference time, conditioned on a prompt, some retrieved context, and whatever tools it decides to call. The same input can produce different outputs. 'Correctness' becomes a probabilistic, evaluative property rather than a binary one. This is not a minor implementation detail - it's a different engineering paradigm, and it's why 'AI Engineering' has emerged as a distinct discipline from both classical software engineering and classical machine learning.\nWhat's actually changing in the day-to-day job of a software engineer:\nSpecification becomes fuzzier and more central. Instead of writing exhaustive if/else logic, engineers write prompts, system instructions, and evaluation rubrics that steer a model's behavior. Getting the specification right is now as important as getting the implementation right - arguably more so. ·\nTesting shifts from unit tests to evals. You still write unit tests for your deterministic code (routing, parsing, tool execution), but the model-facing parts of your system need evaluation harnesses: golden datasets, LLM-as-judge scoring, regression suites that catch prompt drift. ·\nRetrieval and context management become core engineering skills. Because models have finite context and imperfect recall, a huge fraction of production AI engineering is about deciding what information the model sees, in what order, and why - this is RAG, memory design, and context engineering. ·\nOrchestration and tool use replace hand-written business logic in many places. Agents that can call tools, query databases, and chain reasoning steps take over tasks that used to require large amounts of bespoke code. ·\nObservability changes shape. You still need logs and metrics, but you also need to see prompts, completions, token costs, latency per step, and tool-call traces because a bug might not be a stack trace, it might be a subtly wrong instruction fifteen tokens into a system prompt. ·\nNone of this makes classical software engineering obsolete. Quite the opposite production AI systems still need clean APIs, databases, authentication, caching, queues, and deployment pipelines. AI Engineering is best understood as software engineering plus a new, probabilistic component that needs its own discipline of prompt design, retrieval design, evaluation, and guardrails. This handbook treats it that way: roughly half classical backend engineering, half AI-specific engineering, glued together by production practices.\nThe Future of AI Engineering\nA few trends are already visible and worth naming explicitly, because they shape how you should learn:\nAgentic systems are becoming the default interface , not just chatbots. Instead of 'ask a question, get an answer,' production systems increasingly plan, call tools, retrieve data, verify their own output, and take multi-step actions with oversight. Understanding planning, reflection, and multi-agent coordination (Modules 17-20) is quickly becoming as fundamental as understanding REST APIs was a decade ago. 1.\nStandardized interoperability layers are emerging. The Model Context Protocol (MCP) is one of the clearest examples: instead of every framework inventing its own way to expose tools and data sources to a model, MCP standardizes it, the same way HTTP standardized how browsers and servers talk. Learning MCP now is analogous to learning REST in the early 2010s. 2.\nEvaluation and observability are maturing into first-class disciplines , not afterthoughts. Companies that shipped AI features fast in 2023-2024 are now investing heavily in eval infrastructure because 'it seemed to work in the demo' doesn't survive contact with production traffic. 3.\nCost and latency engineering matter as much as accuracy. A model that's 2% more accurate but 5x more expensive and 3x slower is frequently the wrong choice. AI engineers increasingly need to reason about model routing, caching, and quantization/serving trade-offs, not just prompt quality. 4.\nSecurity is catching up to a new threat surface. Prompt injection, data exfiltration through tool calls, and unsafe autonomous actions are real production risks, not academic curiosities. AI Security (Module 25) is no longer optional reading. 5.\nAI Engineer vs. ML Engineer vs. LLM Engineer vs. Prompt Engineer vs. AI Solutions Architect vs. Agentic AI Engineer\nThese titles get used loosely in job postings, which causes real confusion. Here's a grounded comparison based on what each role actually does day to day.\nA useful mental model: ML Engineers build the model. LLM Engineers work close to the model internals. Prompt Engineers get the most out of an existing model through instructions alone. AI/GenAI Engineers build products around models. Agentic AI Engineers build products where the model takes autonomous multi-step action. AI Solutions Architects decide how all of the above fit together at an organizational level.\nThis handbook is built specifically to take you to AI Engineer , with a strong on-ramp into Agentic AI Engineer - the two roles with the fastest-growing hiring demand in 2026, and the roles most directly reachable from a Data Science background.\nWho Should Use This Handbook\nData Scientists who know Python, pandas, and modeling but have never shipped a production API or built an LLM-powered application. ·\nJunior/Backend Developers who are comfortable with software engineering but new to LLMs, embeddings, and agents. ·\nFreshers and career switchers with basic Python literacy who are targeting AI Engineer roles directly. ·\nEngineering teams onboarding new hires into an AI platform team, using this as a structured internal curriculum. ·\nPrerequisites\nBefore starting, you should already be comfortable with:\nPython fundamentals - variables, functions, classes, loops, list/dict comprehensions, virtual environments, pip. ·\nBasic command line usage - navigating directories, running scripts, editing environment variables. ·\nBasic Git - clone, commit, push, pull, branch. ·\nBasic understanding of APIs - what a REST endpoint is, what JSON is, what an HTTP status code means. ·\nBasic SQL - SELECT/INSERT/UPDATE/DELETE, JOINs. ·\nYou do not need: a background in deep learning theory, GPU programming experience, or prior production deployment experience. The standard pattern:\n# config.py import os from dotenv import load_dotenv load_dotenv() OPENAI_API_KEY = os.environ["OPENAI_API_KEY"] ANTHROPIC_API_KEY = os.environ["ANTHROPIC_API_KEY"] GOOGLE_API_KEY = os.environ.get("GOOGLE_API_KEY") # optional, so .get() not []\nUsing os.environ[...] (which raises KeyError if missing) for required keys is a deliberate choice - you want your application to fail loudly at startup if a required key is missing, not fail confusingly three requests later.\nArchitecture\nExamples\nGood Example: Proper Secret Handling\n# main.py from config import OPENAI_API_KEY from openai import OpenAI client = OpenAI(api_key=OPENAI_API_KEY)\nBad Example: Hardcoded Secret (Never Do This)\n# DO NOT DO THIS client = OpenAI(api_key="sk-abc123...") # leaks the moment this is committed\nReal-World Example\nA common enterprise incident pattern: a developer hardcodes a key 'just for testing,' commits it, pushes to a public fork, and within minutes automated scrapers detect the leaked key and abuse it, generating a large unexpected bill before the key is revoked. This module builds that mental model, deliberately avoiding heavy mathematics, so that every later module's engineering decisions (retrieval design, prompt structure, evaluation, cost optimization) rest on real understanding rather than folklore.\nWhy This Topic Matters\nEngineers who treat the LLM as a total black box tend to make the same recurring mistakes: expecting perfect recall from a long context window, being surprised by hallucination, misunderstanding why temperature affects output, and misjudging cost/ latency trade-offs. A correct mental model - even a simplified one - prevents most of these mistakes before they happen.\nIndustry Relevance\nInterviewers for AI Engineer roles routinely probe this exact layer of understanding: not 'can you derive backpropagation,' but 'can you explain why a model might hallucinate a citation' or 'why does output get slower as the response gets longer.' This module is built to make you fluent in exactly that register.\nCommon Misconceptions\n'The model 'looks up' facts like a database.' It doesn't - it generates the statistically most plausible continuation of text based on patterns learned during training. Facts that appear reliably in training data are usually reproduced accurately; facts that are rare, recent, or contradictory in the training data are not. ·\n'A bigger context window means the model perfectly remembers everything in it.' Empirically, model performance degrades with position and density of information in context - this is why retrieval quality (Module 9) and context engineering matter even with huge context windows. ·\n'Temperature = 0 means the model is 'smarter.'' Temperature 0 means deterministic, most-likely-token selection - useful for consistency, but not inherently more accurate, and sometimes worse for tasks that benefit from exploring alternative phrasings. ·\nLearning Objectives\nBy the end of this module, you will be able to:\nExplain, at an engineering level of detail, how a transformer-based LLM generates text token by token. 1.\nExplain tokenization and why it affects cost, context limits, and certain model failure modes. 2.\nExplain the roles of pretraining, instruction-tuning, and RLHF/preference-tuning in producing a usable chat model. 3.\nReason correctly about context windows, and why 'fits in context' doesn't mean 'will be used accurately.' 4.\nExplain sampling parameters (temperature, top-p, top-k, max tokens) and their practical effects. 5.\nExplain why and when models hallucinate, and what does (and doesn't) mitigate it. 6.\nReason about the cost and latency implications of model choice, prompt length, and output length. 7.\nTheory\nFrom Text to Tokens\nLLMs don't process raw characters or whole words - they process tokens , sub-word units produced by a tokenizer (commonly a byte-pair-encoding or similar algorithm). 'Unbelievable' might tokenize as ["Un", "believ", "able"] ; a common word like 'the' is typically a single token. This matters practically because:\nCost is billed per token , input and output separately, not per character or word. ·\nContext limits are measured in tokens , not characters - a 128K-token context window holds roughly 90,000-100,000 English words, but far fewer if the text is code, non-English text, or contains lots of rare tokens (each of which may cost more tokens per unit of meaning). ·\nCertain failure modes (like poor performance on character-level tasks such as counting letters in a word) stem directly from the model never seeing individual characters, only tokens. ·\nHow Generation Actually Happens: Next-Token Prediction\nAt inference time, an LLM is a function that takes a sequence of tokens and outputs a probability distribution over what the next token is likely to be. Text is generated by repeatedly: (1) computing this distribution, (2) sampling one token from it, (3) appending that token to the sequence, and (4) repeating - this is why generation is inherently sequential and why longer outputs take proportionally longer to produce (each new token requires another forward pass through the model, informed by everything generated so far).\nThis is why LLMs are sometimes described as 'extremely sophisticated autocomplete' - that description is directionally correct at the mechanical level, even though what emerges from training at scale (reasoning-like behavior, instruction-following, incontext learning) is far more than the phrase suggests.\nPretraining, Instruction-Tuning, and Preference-Tuning\nA production chat model like GPT, Claude, or Gemini goes through multiple training stages:\nPretraining - the model learns to predict the next token over an enormous, broad corpus of text. This is where most of its world knowledge and language ability comes from, and it's also the most expensive stage by far. 1.\nInstruction-tuning (Supervised Fine-Tuning) - the model is further trained on examples of instructions paired with high-quality responses, teaching it to behave like a helpful assistant rather than a raw text-completion engine. 2.\nPreference-tuning (RLHF / RLAIF / DPO and similar techniques) - the model is further adjusted based on human (or AI-assisted) preference judgments between candidate responses, improving helpfulness, harmlessness, and adherence to intended behavior. 3.\nUnderstanding this pipeline matters practically: it's why base (non-chat) models behave very differently from chat models given the same prompt, why 'jailbreak' attempts specifically target the gap between instruction-tuning and pretrained knowledge, and why different providers' models have different 'personalities' despite similar underlying architectures.\nContext Windows: Capacity Is Not Comprehension\nA context window is the maximum number of tokens (input + output combined, for most providers) a model can process in a single call. It's tempting to treat a large context window (100K+ tokens) as equivalent to a database you can dump everything into - this is a common and costly engineering mistake.\nIn practice:\nModels exhibit positional effects - information in the middle of a very long context is often used less reliably than information near the beginning or end (sometimes called the 'lost in the middle' effect). ·\nIrrelevant or redundant context can dilute attention and degrade output quality, even if it technically 'fits.' ·\nLarger context costs more (you're billed for those input tokens) and increases latency. ·\nThis is the central engineering justification for retrieval-augmented generation (Module 9) - rather than stuffing a huge context window with everything that might be relevant, retrieve only the most relevant, well-ranked pieces of information for the current query.\nSampling Parameters\nA frequent production bug: setting max_tokens too low for a task that requires structured output (e.g., a long JSON array), causing the response to be truncated and therefore invalid JSON - always size max_tokens generously relative to expected output length for structured-output tasks.\nWhy Hallucination Happens\n'Hallucination' - an LLM confidently generating false information - is a direct consequence of how these models work: they generate the most statistically plausible continuation of text, not a verified fact lookup. Hallucination is more likely when:\nThe requested information is rare, obscure, or absent from training data (e.g., very recent events, niche internal company data). ·\nThe prompt implicitly pressures the model to produce an answer even when it doesn't have reliable information (e.g., 'What page is this quote from?' when the model was never shown page numbers). ·\nThe task requires precise structured recall (exact citations, exact numbers) rather than gist-level understanding. ·\nWhat genuinely mitigates hallucination in production: grounding the model in retrieved, verifiable source material (RAG, Module 9) , explicitly instructing the model that it's acceptable to say 'I don't know' , and evaluation/verification steps (Module 22, Module 19's Reflection) - not simply 'asking the model to be more careful,' which has limited effect on its own.\nCost and Latency Engineering\nThree levers dominate production cost and latency:\nModel choice - larger/more capable models cost more per token and are typically slower; smaller/faster models cost less and respond faster but may need more careful prompting or fall back to a larger model for hard cases (a pattern covered in Module 21's model routing). 1.\nInput token count - every token in your prompt (including retrieved context, conversation history, and system instructions) is billed and adds to processing time. 2.\nOutput token count - output generation is inherently sequential (Module 3's 'next-token prediction' mechanics), so longer outputs take proportionally longer and cost proportionally more; max_tokens and prompt instructions that constrain output length are real latency levers, not just cost levers. 3.\nArchitecture\nExamples\nGood Example: Reasoning Correctly About Context\nAn engineer building a customer-support assistant retrieves the 5 most relevant knowledge-base articles (via Module 9's RAG techniques) for each query, rather than stuffing all 4,000 articles into a giant context window - respecting both cost and the 'lost in the middle' effect, and keeping responses fast and accurate.\nBad Example: Misusing Context as a Database\nA team dumps an entire 300-page product manual into the context window on every request 'since the model has a big context window now,' resulting in slow, expensive requests where the model frequently misses details buried in the middle of the document - a direct, avoidable consequence of the positional effects covered in this module's Theory section.\nEnterprise Example\nA legal-tech company's contract-review assistant was confidently citing clause numbers that didn't exist in the uploaded contract. Module 7 introduces a second, equally important model output: embeddings - numerical representations of meaning that make it possible to search, cluster, and compare text (and other content) by semantic similarity rather than exact keyword match. Embeddings are the foundation Module 8 (Vector Databases) and Module 9 (RAG) are built directly on top of - this is the module where 'search by meaning' stops being a vague phrase and becomes a concrete engineering technique.\nWhy This Topic Matters\nEvery RAG system, every semantic search feature, and every 'find similar items' recommendation feature in this handbook's later modules depends on embeddings working correctly. Misunderstanding embeddings - wrong model choice, wrong similarity metric, unnormalized comparisons - is one of the most common root causes of 'our RAG system retrieves irrelevant results' bugs in production.\nIndustry Relevance\nEmbedding model choice, dimensionality, and cost are recurring, concrete production decisions: embedding a large document corpus at scale has real cost and latency implications, and re-embedding an entire corpus because of a model change is expensive enough that the choice deserves real consideration up front, not an afterthought.\nCommon Misconceptions\n'Embeddings and text generation are the same kind of model.' They're both transformer-based, but architecturally and functionally distinct: an embedding model outputs a fixed-size vector representing meaning; a generative model outputs a probability distribution over next tokens. Some providers offer both from related model families, but they serve different purposes and are typically called via different API endpoints. ·\n'Any embedding model will work fine for any task.' Embedding models vary meaningfully in what kind of similarity they capture (e.g., general semantic similarity vs. asymmetric query-document relevance), in dimensionality, in cost, and in domain fit (general text vs. code vs. multilingual). ·\n'Higher-dimensional embeddings are always better.' Higher dimensionality captures more nuance but costs more to store and search, and beyond a point yields diminishing returns for many practical tasks - dimensionality is a real trade-off, not a pure quality dial. ·\nLearning Objectives\nBy the end of this module, you will be able to:\nExplain what an embedding is and how it's produced, at a working engineering level. 1.\nExplain and correctly apply cosine similarity, dot product, and Euclidean distance as similarity metrics. 2.\nChoose an appropriate embedding model for a given task, considering dimensionality, cost, and domain fit. 3.\nImplement text chunking strategies appropriate for embedding and retrieval. 4.\nBuild a basic semantic search feature end-to-end using embeddings. 5.\nRecognize and avoid common embedding pitfalls (mismatched normalization, inappropriate model choice, poor chunking). 6.\nTheory\nWhat an Embedding Actually Is\nAn embedding is a fixed-length vector of floating-point numbers (e.g., 1536 dimensions for a common OpenAI embedding model) that represents the meaning of a piece of text, produced by passing that text through a trained embedding model. The key property that makes embeddings useful: texts with similar meaning produce vectors that are close together in this high-dimensional space , while texts with dissimilar meaning produce vectors that are far apart.\n"The cat sat on the mat"     -> [0.021, -0.114, 0.302, ..., 0.056]   (1536 numbers) "A feline rested on the rug"  -> [0.019, -0.108, 0.297, ..., 0.061]   (close to the above) "Quarterly revenue rose 12%"   -> [0.412, 0.033, -0.201, ..., -0.187]  (far from both above)\nCrucially, this closeness captures semantic similarity, not lexical overlap - the first two sentences share almost no exact words but are close in embedding space, which is precisely what makes embeddings more powerful than keyword search for many tasks.\nSimilarity Metrics\nPractically: always check your embedding provider's documentation for the recommended similarity metric - using the wrong one against a model's actual training assumptions silently degrades result quality without throwing any error, a very easy mistake to make and a very hard one to notice without deliberate evaluation.\nimport numpy as np def cosine_similarity(a: np.ndarray, b: np.ndarray) -> float: return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))\nChoosing an Embedding Model\nKey dimensions of comparison:\nGeneral-purpose vs. domain-specific - a general text embedding model handles broad natural language well; code-specific or domain-specific (legal, medical, multilingual) embedding models can meaningfully outperform general models within their domain. ·\nSymmetric vs. asymmetric similarity - some models are trained for symmetric similarity (comparing two similar pieces of text), others explicitly for asymmetric query-document retrieval (a short query vs. a long document) - using a symmetrictrained model for asymmetric retrieval, or vice versa, is a real, common source of poor retrieval quality. ·\nDimensionality - higher dimensionality (e.g., 3072 vs. 1536) generally captures more nuance at the cost of storage and search speed; several modern embedding APIs support configurable/truncatable dimensionality, letting you trade off quality against cost directly. ·\nCost and latency - embedding a large corpus is a real, sometimes substantial, one-time (and ongoing, for new content) cost; factor this into model choice, not just per-query quality. ·\nText Chunking for Embeddings\nBecause embedding models have input length limits, and because embedding an entire long document into one vector loses fine-grained retrievability (a 50-page document embedded as a single vector can't help you find the one relevant paragraph ), documents are typically split into chunks before embedding. Chunking strategy is a genuine, high-leverage engineering decision, not a minor detail:\nFixed-size chunking (e.g., every 500 tokens) - simple, predictable, but can split sentences or logical sections awkwardly mid-thought. ·\nSentence/paragraph-boundary chunking - respects natural language boundaries, generally producing more coherent, retrievable chunks. ·\nOverlapping chunks (e.g., 500 tokens with 50 tokens of overlap between consecutive chunks) - reduces the risk of splitting a relevant fact exactly across a chunk boundary, at the cost of some storage redundancy. ·\nStructure-aware chunking (by heading, by section, by function/class for code) often the highest-quality approach when the source content has clear structure to exploit. ·\ndef chunk_text(text: str, chunk_size_tokens: int = 500, overlap_tokens: int = 50) -> list[str]: tokens = tokenizer.encode(text) chunks = [] start = 0 while start < len(tokens): end = min(start + chunk_size_tokens, len(tokens)) chunks.append(tokenizer.decode(tokens[start:end])) start += chunk_size_tokens - overlap_tokens return chunks\nChunk size directly trades off against Module 3's 'lost in the middle' concerns and retrieval precision: chunks too large dilute relevance (a chunk about three different topics is a poor match for any single-topic query); chunks too small lose necessary context (a chunk with a pronoun but not its antecedent). This trade-off is explored further, with concrete tuning guidance, in Module 9.\nA Minimal Semantic Search Pipeline\nasync def build_search_index(documents: list[str]) -> list[tuple[str, np.ndarray]]: chunks = [chunk for doc in documents for chunk in chunk_text(doc)] embeddings = await embed_batch(chunks) # one API call for many chunks, where supported return list(zip(chunks, embeddings)) async def semantic_search(query: str, index: list[tuple[str, np.ndarray]], top_k: int = 5) -> list[str]: query_embedding = await embed_text(query) scored = [ (chunk, cosine_similarity(query_embedding, chunk_embedding)) for chunk, chunk_embedding in index ] scored.sort(key= lambda x: x[1], reverse=True) return [chunk for chunk, score in scored[:top_k]]\nThis in-memory version doesn't scale past a small corpus - Vector databases solve this with Approximate Nearest Neighbor (ANN) indexing algorithms - most commonly HNSW (Hierarchical Navigable Small World graphs) or IVFFlat (Inverted File Index) - which organize vectors into structures that allow finding approximately the closest matches in sublinear time, trading a small, usually acceptable, amount of recall for large speed gains.\nExact search:  O(n) - check every vector, guaranteed correct top-K ANN search:    O(log n) or better - check a small, well-chosen subset, approximately correct top-K (typically >95% recall with proper tuning)\npgvector: Vector Search Inside PostgreSQL\nGiven this handbook's stack, pgvector is the primary production tool covered here. It adds a vector column type and similarity operators directly to Postgres:\nCREATE EXTENSION IF NOT EXISTS vector; CREATE TABLE document_chunks ( id BIGSERIAL PRIMARY KEY , document_id UUID NOT NULL , chunk_text TEXT NOT NULL , chunk_index INT NOT NULL , embedding VECTOR(1536) NOT NULL , metadata JSONB DEFAULT '{}', created_at TIMESTAMPTZ DEFAULT now() ); -- HNSW index for fast approximate cosine similarity search CREATE INDEX ON document_chunks USING hnsw (embedding vector_cosine_ops);\n-- Find the 5 most similar chunks to a query embedding, filtered by metadata SELECT chunk_text, 1 - (embedding <=> $1) AS similarity FROM document_chunks WHERE metadata->>'source_type' = 'policy_document' ORDER BY embedding <=> $1 LIMIT 5;\nThe <=> operator computes cosine distance directly in SQL; 1 - distance converts it to the more intuitive similarity score used throughout Module 7. Combining a WHERE clause on regular columns/JSONB metadata with vector ordering in the same query is exactly the 'metadata filtering alongside similarity search' capability that makes a real vector database meaningfully more useful than Module 7's minimal pipeline.\npgvector vs. Dedicated Vector Databases\nThe practical guidance this handbook gives: start with pgvector if you're already running Postgres and your scale is moderate (up to tens of millions of vectors is often comfortably within reach) ; migrate to or add a dedicated vector database when you have a specific, demonstrated need - extreme scale, specialized ANN tuning, or vector-search-specific features pgvector doesn't yet offer - not preemptively.\nIndexing Trade-offs\nIndex parameters are real tuning knobs, not 'set and forget': higher ef_construction / m (HNSW) or more lists / probes (IVFFlat) improve recall at the cost of build time, index size, and query latency - the right setting depends on your corpus size and latency/recall requirements, and should be validated empirically (Module 9 covers retrieval evaluation methodology directly).\nSchema Design for Filtered Retrieval\nReal production retrieval is rarely 'search the entire corpus' - it's usually 'search within this user's documents,' 'search only recent content,' or 'search only a specific document type.' Its limitations become apparent with larger, messier corpora, ambiguous queries, or queries requiring information spread across multiple chunks - which is why production RAG systems typically add the techniques below.\nRe-Ranking\nRaw vector similarity search (Module 8) is fast but imprecise - it optimizes for retrieval speed over a large corpus, not for finding the single best-matching chunks. Re-ranking adds a second, more expensive but more accurate relevance-scoring step\nover a smaller candidate set:\nRe-rankers are typically cross-encoder models - unlike embedding models, which encode query and document separately then compare vectors, a cross-encoder processes the query and each candidate document together , capturing finer-grained relevance signals at the cost of being too slow to run over an entire large corpus (hence running it only over the smaller candidate set from the first-pass vector search).\nasync def retrieve_with_reranking(query: str, top_k_candidates: int = 50, top_k_final: int = 5) -> list[Chunk]: query_embedding = await embed_text(query) candidates = await vector_search(query_embedding, top_k=top_k_candidates) reranked = await reranker.score(query, [c.text for c in candidates]) return [c for c, score in sorted(zip(candidates, reranked), key= lambda x: x[1], reverse=True)][:top_k_final]\nQuery Transformation\nThe user's literal query is not always the best search query. Several techniques address this:\nQuery expansion - generate a few alternative phrasings of the query (via the LLM itself) and retrieve for each, merging results - helps when the user's phrasing doesn't lexically/semantically match the corpus's phrasing. ·\nHyDE (Hypothetical Document Embeddings) - ask the LLM to generate a hypothetical answer to the query first, then embed that hypothetical answer (rather than the query) for retrieval - often improves retrieval because a hypothetical answer's embedding is closer in style/content to actual relevant documents than a short question's embedding is. ·\nMulti-query decomposition - for complex queries genuinely requiring multiple pieces of information ('compare X and Y's pricing and support policies'), decompose into sub-queries, retrieve for each separately, and combine - directly relevant to Module 17-18's agentic planning concepts. ·\nasync def hyde_retrieve(query: str, top_k: int = 5) -> list[Chunk]: hypothetical_answer = await llm.complete(f"Write a short, plausible answer to: {query}") hypothetical_embedding = await embed_text(hypothetical_answer) return await vector_search(hypothetical_embedding, top_k=top_k)\nHybrid Search\nSemantic (vector) search excels at conceptual/paraphrase matching but can underperform on queries requiring exact terms - product codes, error messages, proper nouns, acronyms - where traditional keyword search (BM25 or Postgres fulltext search, previewed in Module 8) is often more reliable. Hybrid search combines both signals:\nasync def hybrid_search(query: str, top_k: int = 5, vector_weight: float = 0.6) -> list[Chunk]: vector_results = await vector_search( await embed_text(query), top_k=20) keyword_results = await fulltext_search(query, top_k=20) combined_scores = combine_and_normalize_scores(vector_results, keyword_results, vector_weight) return sorted(combined_scores, key= lambda x: x.score, reverse=True)[:top_k]\nThe combination weighting ( vector_weight ) is a real tuning parameter, best set empirically against an evaluation set (this module's Evaluation section) rather than guessed - some corpora and query patterns favor keyword signal more heavily than others.\nGrounded Prompt Construction and Citation\nHow retrieved chunks are formatted into the prompt directly affects both answer quality and the ability to cite sources - both matter for trust in production systems:\ndef build_rag_prompt(query: str, chunks: list[Chunk]) -> str: context_block = "\\n\\n".join( f"[Source {i+1}: {c.document_title}]\\n{c.text}" for i, c in enumerate(chunks) ) return f""" Answer the question using ONLY the information in the sources below. Cite sources using [Source N] notation. If the sources don't contain enough information to answer, say so explicitly rather than guessing. Sources: {context_block} Question: {query} """\nThis directly implements Module 3's most effective hallucination mitigation (grounding in verifiable content) and Module 4's structured-prompt discipline (explicit constraints: 'ONLY,' 'say so explicitly rather than guessing') in one concrete pattern.\nEvaluating RAG Systems: Retrieval vs. Generation\nRAG quality problems have two distinct possible root causes, and conflating them wastes debugging time:\nRetrieval failure - the relevant information was never retrieved in the first place; no prompt engineering can fix this, because the LLM never saw the needed information. Diagnosed by checking, independent of generation, whether the retrieved chunks actually contain the answer (a 'retrieval recall' metric). ·\nGeneration failure - the relevant information was retrieved, but the LLM failed to use it correctly (missed it, misread it, or hallucinated despite it being present). Diagnosed by checking, given the actual retrieved chunks, whether the generated answer correctly reflects them. ·\nclass RAGEvalCase(BaseModel): query: str expected_answer_contains: list[str] relevant_chunk_ids: list[str] def evaluate_retrieval(case: RAGEvalCase, retrieved_chunks: list[Chunk]) -> bool: retrieved_ids = {c.id for c in retrieved_chunks} return bool(retrieved_ids & set(case.relevant_chunk_ids)) # did we retrieve at least one relevant chunk? def evaluate_generation(case: RAGEvalCase, answer: str) -> bool: return all(phrase.lower() in answer.lower() for phrase in case.expected_answer_contains)\nThis two-part evaluation is a lightweight preview of Module 22's full evaluation methodology, applied specifically to RAG's two-stage architecture -
